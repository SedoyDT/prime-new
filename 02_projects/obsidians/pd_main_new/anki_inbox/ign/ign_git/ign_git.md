Чтобы вернуть изменения из stash (восстановить их в рабочее состояние), можно использовать команду `git stash pop` или `git stash apply`. Вот как они работают:::


### 1. `git stash pop`
Эта команда восстанавливает последние сохраненные изменения из stash и удаляет их из списка stash.

```
git stash pop
```

### 2. `git stash apply`
Эта команда также восстанавливает изменения из stash, но **не** удаляет их из списка stash. Это полезно, если вы хотите применить изменения, но оставить их в stash для возможного повторного использования.

```
git stash apply
```

### Если у вас есть несколько записей в stash:
- По умолчанию обе команды работают с самой последней записью в stash. 
- Если вам нужно применить более раннюю запись, вы можете указать её индекс, например:

```
git stash apply stash@{2}
```
или
```
git stash pop stash@{2}
```

Здесь `stash@{2}` означает третью запись в списке stash (нумерация начинается с 0).

### Дополнительная информация:
- После применения stash, если возникает конфликт, Git сообщит об этом, и вы сможете вручную разрешить конфликты, как при обычном мержинге.
- Чтобы просмотреть список всех записей в stash, используйте команду:

```
git stash list
```

Таким образом, вы можете вернуть нужные изменения из stash и продолжить работу.

# Вот 20 нетривиальных задач по Git, ориентированных на работу с удалёнными репозиториями:
<!-- basicblock-start  deck='ign_git' -->
Вот 20 нетривиальных задач по Git, ориентированных на работу с удалёнными репозиториями:::


### Задачи на управление ветками
1. **Управление удалёнными и локальными ветками**: Создайте новую ветку, сделайте несколько коммитов и отправьте её в удалённый репозиторий. Затем удалите локальную ветку и восстановите её из удалённого репозитория.

2. **Синхронизация удалённой ветки с несколькими локальными копиями**: Клонируйте репозиторий на два разных устройства, создайте новую ветку в одном из них, внесите изменения и отправьте их в удалённый репозиторий. Затем синхронизируйте изменения с другим устройством.

3. **Удаление удалённой ветки**: Создайте ветку, отправьте её в удалённый репозиторий, а затем удалите её как локально, так и удалённо. Убедитесь, что ветка полностью удалена из всех источников.

### Задачи на синхронизацию с удалённым репозиторием
4. **Конфликты при `git pull`**: Создайте ситуацию, когда на удалённом и локальном репозиториях в одной и той же ветке происходят параллельные изменения. Выполните `git pull` и решите возникшие конфликты.

5. **Настройка нескольких удалённых репозиториев**: Добавьте второй удалённый репозиторий к существующему локальному репозиторию, затем отправьте изменения в оба репозитория и убедитесь, что они синхронизированы.

6. **Использование `git fetch` и `git merge` вместо `git pull`**: Выполните `git fetch` для загрузки последних изменений из удалённого репозитория без их слияния. Затем вручную выполните `git merge`, чтобы интегрировать изменения, и проанализируйте разницу с `git pull`.

### Задачи на работу с форками и pull request'ами
7. **Создание и синхронизация форка**: Форкните репозиторий на GitHub или другой платформе, сделайте изменения в форке, а затем отправьте pull request в оригинальный репозиторий.

8. **Решение конфликтов при обновлении форка**: Обновите свой форк до актуальной версии оригинального репозитория, если в нём произошли изменения, которые конфликтуют с вашими локальными изменениями.

9. **Изменение и обновление pull request'а**: Создайте pull request с изменениями в форке, затем внесите дополнительные изменения в ту же ветку и обновите pull request.

### Задачи на работу с GitHub Actions или аналогичными CI/CD системами
10. **Автоматическое тестирование при push'е**: Настройте GitHub Actions или другую CI/CD систему для автоматического тестирования кода при каждом push'е в удалённый репозиторий. Проанализируйте, как это влияет на процесс разработки.

11. **Публикация артефактов**: Настройте workflow в GitHub Actions, который будет публиковать артефакты (например, сборки) при каждом релизе в удалённый репозиторий.

### Задачи на работу с тегами и релизами
12. **Создание и публикация тегов**: Создайте несколько тегов в репозитории и отправьте их в удалённый репозиторий. Затем переместите один из тегов на другой коммит и обновите его в удалённом репозитории.

13. **Создание релиза на основе тега**: Создайте релиз в GitHub или другой платформе на основе ранее созданного тега, включив в релиз описание и необходимые артефакты.

### Задачи на управление доступом
14. **Ограничение прав доступа**: Настройте удалённый репозиторий таким образом, чтобы разные пользователи имели разные уровни доступа (например, только чтение, возможность push'а в определённые ветки). Проверьте работу этих ограничений.

15. **Настройка SSH-доступа**: Настройте SSH-доступ к удалённому репозиторию и выполните push и pull с использованием SSH-ключей вместо HTTPS.

### Задачи на работу с подмодулями
16. **Добавление и синхронизация подмодуля**: Добавьте в репозиторий подмодуль, отправьте изменения в удалённый репозиторий, затем клонируйте репозиторий в другой каталог и инициализируйте подмодуль. Убедитесь, что подмодуль синхронизирован.

17. **Обновление подмодуля и синхронизация изменений**: Обновите код в подмодуле, а затем синхронизируйте изменения в основном репозитории и убедитесь, что всё работает корректно.

### Задачи на восстановление и откат изменений
18. **Восстановление удалённого файла из истории**: Удалите файл в локальном репозитории, закоммитьте и отправьте изменения в удалённый репозиторий. Затем восстановите этот файл из истории коммитов.

# Вот 20 нетривиальных задач по Git для углублённой практики:
<!-- basicblock-start  deck='ign_git' -->
Вот 20 нетривиальных задач по Git для углублённой практики:::


### Задачи на ветвление и слияние
1. **Слияние с конфликтами**: Создайте две ветки, внесите изменения в один и тот же файл в обеих ветках, затем попробуйте их слить. Разрешите возникшие конфликты вручную.
  
2. **Rebase vs. Merge**: Создайте ветку, сделайте в ней несколько коммитов, затем выполните `git rebase` и `git merge` этой ветки в основную. Сравните историю коммитов в обоих случаях.

3. **Cherry-pick**: Внесите серию изменений в одну ветку, затем выполните `cherry-pick` отдельных коммитов из этой ветки в основную. Проанализируйте, как эти коммиты вписываются в историю основной ветки.

### Задачи на работу с историей коммитов
4. **Переписывание истории (`git rebase -i`)**: Создайте несколько коммитов в одной ветке. Используйте `git rebase -i`, чтобы изменить порядок коммитов, объединить их, изменить сообщения или удалить ненужные.

5. **Отмена коммитов**: Создайте несколько коммитов, затем используйте `git revert`, `git reset` и `git checkout` для отмены или возврата изменений. Проанализируйте, чем отличаются эти подходы.

6. **Исправление последнего коммита (`git commit --amend`)**: Внесите изменения в файл, сделайте коммит, а затем используйте `git commit --amend`, чтобы изменить сообщение коммита или добавить дополнительные изменения.

### Задачи на работу с удалёнными репозиториями
7. **Создание pull request без прямого доступа**: Форкните репозиторий, создайте ветку с изменениями и отправьте их через pull request в исходный репозиторий.

8. **Использование `git fetch` vs `git pull`**: Выполните `git fetch` и `git pull` для синхронизации локального репозитория с удалённым. Проанализируйте разницу между этими командами.

9. **Удаление удалённой ветки**: Создайте удалённую ветку, затем удалите её с локального и удалённого репозиториев. Убедитесь, что ветка полностью удалена.

### Задачи на работу с `.gitignore`
10. **Создание и настройка `.gitignore`**: Создайте файл `.gitignore`, добавьте в него правила для игнорирования определённых файлов и директорий. Убедитесь, что Git не отслеживает эти файлы.

11. **Игнорирование уже отслеживаемых файлов**: Добавьте файл в `.gitignore`, который уже находится под управлением Git. Настройте репозиторий так, чтобы Git перестал его отслеживать, но не удалял из рабочей директории.

### Задачи на восстановление и откат изменений
12. **Восстановление удалённой ветки**: Удалите локальную и удалённую ветку, а затем восстановите её из reflog.

13. **Восстановление удалённого файла**: Удалите файл, закоммитьте изменения, затем используйте `git checkout` или `git restore` для восстановления этого файла из истории.

14. **Откат к определённому коммиту**: Используйте `git reset` для возврата состояния репозитория к конкретному коммиту. Проанализируйте, как различаются `--soft`, `--mixed`, и `--hard` режимы.

### Задачи на работу с подмодулями
15. **Добавление подмодуля**: Создайте новый проект, добавьте в него подмодуль, затем клонируйте этот проект в другой каталог и инициализируйте подмодуль.

16. **Обновление подмодуля**: Обновите код в подмодуле, а затем синхронизируйте изменения в основном репозитории.

### Задачи на работу с большими файлами
17. **Настройка Git LFS**: В репозитории с большими файлами настройте и используйте Git LFS для отслеживания этих файлов. Проанализируйте, как LFS изменяет размер репозитория.

### Задачи на сложные сценарии слияния
18. **Rebase сложной истории**: Создайте несколько веток с различными изменениями, затем выполните rebase одной ветки на другую с множественными конфликтами. Попробуйте разрешить все конфликты.

19. **Слияние с неустранимыми конфликтами**: Создайте сценарий, где при слиянии двух веток возникают такие конфликты, которые не удаётся разрешить (например, конфликтующие изменения в бинарных файлах). Откатите слияние и найдите другой способ интеграции изменений.

### Задачи на работу с тегами
20. **Создание и управление тегами**: Создайте несколько тегов в репозитории, затем переместите один из тегов на другой коммит. Удалите локальный и удалённый теги.

Эти задачи охватывают широкий спектр возможностей Git и позволяют углубить понимание того, как Git работает в различных сценариях.

# Что такое git hooks?
<!-- basicblock-start  deck='ign_git' -->
Что такое git hooks?::


Git hooks - это сценарии, которые запускаются при выполнении определенных действий в системе контроля версий Git. Они позволяют автоматизировать различные задачи, такие как проверка кода перед коммитом, уведомление других разработчиков о новых изменениях, создание резервных копий и т.д. Git hooks могут быть написаны на любом языке программирования и запускаются автоматически при выполнении определенных команд в Git. Это позволяет разработчикам оптимизировать процесс разработки и упростить управление проектом.
